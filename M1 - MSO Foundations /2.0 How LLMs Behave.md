### 1. Problem Statement

Software engineers building AI applications frequently attempt to evaluate feature correctness using conventional unit testing patterns, such as exact string assertions (`assert output == expected_text`). Because large language models operate probabilistically through token sampling, identical prompt inputs produce varying text outputs. Relying on rigid string matching leads to false test failures, fragile CI/CD build pipelines, and an inability to assess true structural compliance or semantic accuracy.

---

### 2. Summary

The [MSO Foundations](https://anthropic-partners.skilljar.com/path/claude-certified-developer-foundations/mso-foundations/486742/scorm/1zuxexjatih0p) module details fundamental model mechanics and evaluation methodologies necessary for developing robust Claude applications:

* **Token Processing & Context Budget**: Language models consume and generate text via subword tokens. The context window is a fixed shared resource that encapsulates system prompts, multi-turn history, tool definitions, and output generation limits (`max_tokens`).
* **Sampling & Non-Determinism**: Autoregressive next-token prediction relies on probability distributions configured by sampling hyperparameters (`temperature`, `top_p`). Non-determinism is the core output characteristic of sampling, meaning identical input payloads do not guarantee identical text outputs.
* **Invariant Property Assertions**: Testing strategies must pivot from exact string matching to validating invariant structural properties—such as verifying JSON schema parsing, checking for mandatory key-value fields, or validating numerical value ranges.
* **Evals & Model-Graded Judges**: When evaluating semantic quality, tone, or nuanced adherence rather than strict syntax, developers must implement continuous evaluation suites (evals) utilizing model-graded judges to score output correctness.

### 3. Clear & Simple Explanation

* **Claude Predicts Probabilities, Not Rigid Text**: Because Claude generates answers by calculating token probabilities (sampling), re-running the exact same prompt can yield slightly different wording while conveying the identical meaning.
* **Assert on Rules, Not Exact Phrasing**: When writing automated tests for Claude features, never assert that the returned string matches an exact block of text. Instead, test structural rules: Is the response valid JSON? Is the required `customer_id` key present? Is the confidence score within expected numeric limits?
* **Use Model-Graded Evals for Meaning**: When checking subjective or semantic qualities (such as whether an answer is helpful or polite), use an evaluation framework where a secondary Claude instance acts as an automated judge to score the output.

### 5. Key Terms Note Section

Developing production-ready features on [MSO Foundations](https://anthropic-partners.skilljar.com/path/claude-certified-developer-foundations/mso-foundations/486742/scorm/1zuxexjatih0p) requires managing **Subword Tokenization** across a finite **Context Window**. Developers configure **Sampling Hyperparameters** that drive **Autoregressive Token Prediction**, which inherently introduces **Non-Determinism**. To evaluate non-deterministic features, engineers must implement **Property Assertions** for structural verification and **Model-Graded Judges** within formal **Evals** to measure semantic accuracy.

**Key Technical Terms**

* **Subword Tokenization**: The process of dividing input and output text into subword numerical units (tokens) processed by the model.
* **Context Window**: The maximum shared token capacity available for prompt inputs, system context, tool schemas, and generated completions in a single API request.
* **Sampling Hyperparameters**: Configuration parameters (such as `temperature` and `top_p`) that control token selection randomness and probability distributions.
* **Autoregressive Token Prediction**: The iterative generation mechanism where an LLM predicts each subsequent token based on the probability distribution derived from preceding tokens.
* **Non-Determinism**: The property of generative models where identical input prompts produce varying token completions across separate executions due to sampling.
* **Property Assertions**: Programmatic code tests that evaluate structural invariants (e.g., schema validation, field existence, numeric boundaries) rather than exact string equality.
* **Model-Graded Judge**: An evaluation strategy where a language model is prompted to evaluate, score, or benchmark the semantic quality and accuracy of another model's output.
* **Evals (Evaluations)**: Systematic test suites designed to continuously evaluate LLM performance, accuracy, and compliance across non-deterministic outputs.
