# Model options and reasoning modes

### 1. Problem Statement

When developing enterprise applications with modern Large Language Models, engineering teams often confuse model tier selection with reasoning capability configuration. Passing legacy parameters like fixed token budgets for reasoning can lead to runtime API failure (HTTP 400 errors), while applying uncalibrated reasoning to simple tasks causes unnecessary latency and cost inflation. Developers need a clear architectural pattern to decouple model selection from request-level reasoning controls.

---

### 2. Summary

* **Two Orthogonal Levers**: Model choice (family selection) and reasoning mode are independent decisions that compose per API call.
* **Adaptive Thinking Mechanism**: Current model generations use adaptive thinking, where the model dynamically decides when and how much to reason based on prompt complexity.
* **Effort Control vs. Deprecated Parameters**: Depth of reasoning is controlled via an `effort` setting. The legacy `budget_tokens` parameter is deprecated and results in an HTTP 400 error on the latest model generations.
* **Output Payload Management**: Thinking content is omitted from API responses by default on newer models. If thinking visibility is required, applications must explicitly request summarized display.
* **Cost & Latency Optimization**: Reasoning carries significant latency and token cost; it should be reserved for complex, multi-step tasks, whereas lookups and simple text classifications should run with minimal or disabled reasoning.
* **Default Verification**: Default thinking configurations vary across models (some execute adaptive thinking by default or mandatorily), requiring build-time verification against technical documentation.

---

### 3. Clear & Simple Explanation

Think of picking a model like choosing a car (e.g., a baseline sedan vs. a heavy-duty truck). Choosing whether to enable reasoning is like choosing whether to activate "Sport Mode" during a specific drive.

1. **Model Choice**: Defines the core strength and intelligence baseline.
2. **Reasoning Mode**: Defines how much deep thinking the model performs for a *specific task*.
3. **Adaptive Thinking & Effort**: Instead of telling the model "think for exactly 500 tokens," you adjust an **effort** dial. The model then decides when it needs to pause and reason through a complex problem.
4. **When to use it**: Turn up effort for multi-step logic, edge-case math, or complex code generation. Dial it down or turn it off for standard database lookups or routing rules to save time and API costs.

### 4. Real-World Application

**Scenario: Multi-Agent Automated Support & Escalation Engine**

An enterprise system processes customer support workflows containing both straightforward data lookups (e.g., "Where is my order?") and complex policy troubleshooting (e.g., multi-tier billing dispute resolution).

```
                      [ Incoming Customer Request ]
                                    │
                                    ▼
                         [ API Gateway & Router ]
                                    │
            ┌───────────────────────┴───────────────────────┐
            ▼                                               ▼
   [ Fast Triage Agent ]                          [ Resolution Agent ]
   • Model: Baseline Tier                         • Model: High-Capability Tier
   • Reasoning Mode: Effort = Low/Disabled        • Reasoning Mode: Effort = High
   • Output: Direct JSON Route                    • Output: Reasoning + Solution
            │                                               │
            ▼                                               ▼
   (Simple Lookup / Classification)               (Complex Dispute Logic)
   • Zero wasted thinking tokens                  • Adaptive multi-step analysis
   • Minimal Latency                              • Omitted raw thinking by default

```

**Architecture Implementation Key Points:**

* **Simple Router**: Directs routine tasks with low/disabled reasoning effort to eliminate latency.
* **Complex Resolver**: Enables high adaptive reasoning effort for intricate business logic.
* **API Safety**: Uses the `effort` parameter instead of legacy token budgets to prevent HTTP 400 runtime exceptions.

---

### 5. Key Technical Terms

* **Reasoning Mode**: A per-request API setting that determines whether and how deeply a model evaluates a prompt prior to returning its final output.
* **Adaptive Thinking**: An engine-level behavior where the model dynamically assesses prompt complexity to determine the duration and structure of its reasoning process.
* **Effort Setting**: The API configuration parameter used to tune the depth of adaptive thinking for a given request.
* **`budget_tokens`**: A legacy configuration parameter for setting explicit reasoning token limits, now deprecated and resulting in an HTTP 400 error on modern model generations.
* **Summarized Display**: An API response option requested when thinking tokens (omitted by default) need to be visible in a condensed format for debugging or user transparency.

1. An engineer updating an older Claude API integration notices that request calls are failing with an HTTP 400 error on the latest model generation. What is the most likely cause of this failure?

* A) The application requested an effort setting without specifying a high-capability model tier.
* B) The application attempted to retrieve summarized display tokens on a classification prompt.
* C) The application passed the deprecated `budget_tokens` parameter instead of using the `effort` setting.
* D) The API payload omitted the system prompt required for adaptive thinking.

* A) Model selection and reasoning mode are composable, independent levers configured per API request.
* B) Enabling reasoning automatically upgrades the request to the highest model tier available.
* C) Reasoning mode is globally locked at the model family level and cannot be modified per request.

3. A lead AI architect is auditing an enterprise workflow to reduce API latency and cost. Which workload is the POOREST candidate for high-effort adaptive thinking?

* A) Multi-file code refactoring and dependency analysis.
* B) Root-cause analysis for intermittent database lockouts.
* C) Multi-step legal contract clause reconciliation.

4. When executing requests on the newest Claude model generations with adaptive thinking enabled, how is thinking content handled in the API response by default?

* A) Extended raw thinking tokens are included at the beginning of the standard message content block.
* B) Thinking content is completely omitted from the response unless summarized display is explicitly requested.
* C) Thinking content is automatically written to a separate HTTP trailer header.
* D) The API returns an error if the client application does not provide a designated streaming callback for thinking tokens.

---

5. How does adaptive thinking adjust its depth when processing a prompt?

* A) The developer specifies a fixed token count that the model must consume before generating an answer.
* B) The API server selects a random token depth based on current region availability.
* C) The model dynamically evaluates when and how much to think based on the prompt, tuned via an effort setting.
* D) The depth is governed exclusively by the total context length of historical messages in the conversation.

---

--- **Answer Key & Explanations** ---

1. **C** - On the newest model generations, the legacy `budget_tokens` parameter is deprecated and explicitly returns an HTTP 400 error. Developers must use the `effort` parameter to tune adaptive thinking depth.
2. **A** - Model selection (family member) and reasoning mode (effort/thinking settings) are separate, orthogonal decisions that compose per individual API call.
3. **D** - Reasoning earns its computational cost on complex, multi-step problems. Allocating reasoning tokens to simple lookups, classification, or metadata extraction wastes API budget and increases unnecessary latency.
4. **B** - On the newest model generations, thinking content is omitted from response payloads by default. Developers must specifically request summarized display when they need to inspect or show reasoning outputs.
5. **C** - Under adaptive thinking, the model autonomously determines when and how much reasoning is required for a prompt, with overall depth guided by the `effort` setting rather than rigid token boundaries.
