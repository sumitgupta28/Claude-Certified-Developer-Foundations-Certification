### 1. Problem Statement

Application architects must select the appropriate API execution pattern (synchronous, streaming, or asynchronous batch) based on latency constraints, user experience requirements, and throughput demands. Choosing the wrong communication pattern can lead to poor perceived frontend latency, server connection timeouts during long generations, or inefficient resource utilization during bulk background processing.

---

### 2. Summary

* **Synchronous Requests**: The application sends a single request and blocks until the entire model output is completely generated and returned in a single JSON payload. Best suited for short outputs, automated backend jobs, or non-interactive workflows where real-time progress visibility is unnecessary.
* **Streaming via Server-Sent Events (SSE)**: Enables progressive token rendering by pushing completion fragments over the open HTTP connection as Claude generates them. This drastically reduces perceived latency (Time to First Token) and prevents HTTP timeouts on long-form content generation.
* **Asynchronous / Batch Workloads**: Decouples request dispatch from output retrieval for high-volume, non-interactive tasks, providing higher throughput and cost efficiency for offline operations.
* **Client-Side Responsibilities**: When consuming streams, client application code is responsible for receiving SSE event fragments, reassembling them into the final structured message payload, and gracefully handling or recovering from stream interruptions.

---

### 3. Clear & Simple Explanation

Communicating with Claude can be understood through three real-world ordering scenarios:

* **Synchronous**: Ordering a sandwich at a counter and standing still until the entire meal is cooked, packaged, and handed to you in one bag. If the meal takes a long time, you stand there waiting with zero updates until it is finished.
* **Streaming**: Watching a coffee machine fill your cup drip-by-drip. You see the cup filling immediately, so you don't feel like you are sitting in the dark waiting for a complete pot to boil.
* **Asynchronous (Batch)**: Submitting a wholesale order for 10,000 crates of coffee to be delivered to a warehouse overnight. You don't stand at the counter waiting; you submit the job, leave, and retrieve the full batch results when processing completes later.

### 5. Key Terms Note Section

When integrating the technical substrate within the [MSO Foundations](https://anthropic-partners.skilljar.com/path/claude-certified-developer-foundations/mso-foundations/486742/scorm/1zuxexjatih0p) curriculum, developers must maintain strict terminology surrounding network transport protocols and execution models.

**Key Technical Terms**

* **Synchronous Execution**: A blocking API call pattern where the client waits for the server to process the prompt completely before receiving the entire response payload at once.
* **Streaming**: A execution mode where model output tokens are sent to the client incrementally as they are generated, rather than waiting for completion.
* **Server-Sent Events (SSE)**: An HTTP-based protocol that enables a server to continuously push real-time data updates down an established persistent HTTP connection to a client.
* **Asynchronous Processing**: An unblocked execution model where tasks are submitted to a queue for background execution, allowing results to be polled or retrieved later.
* **Time to First Token (TTFT)**: The duration between issuing an API request and receiving the very first token of generated output, serving as a primary metric for perceived latency.
* **Payload Reassembly**: The client-side process of aggregating individual streaming event fragments into a complete, coherent message object.
