### Failure Handling & Model Selection

### 1. Problem statement

Production traffic exposes AI applications to operational failures that developmental testing rarely uncovers, such as rate limits, temporary server overloads, malformed tool payloads, and authentication failures. Blindly retrying every failed API request wastes token budgets, elevates latency, and causes execution loops, while failing to retry transient network glitches leads to unnecessary application outages.

---

### 2. Summary

* **The Retriable vs. Terminal Test**: Evaluate every failure with one core question: *Would waiting and trying the exact same request again plausibly work?*
* **Retriable Failures**: Transient issues (e.g., HTTP 429 rate limit responses, HTTP 502/503 temporary server overloads, network timeouts) where the same request will likely succeed once resources clear.
* **Terminal Failures**: Unrecoverable execution errors (e.g., malformed payloads, schema validation errors, 401/403 authentication failures, context window length violations) where re-issuing the identical request will fail every time.
* **Model Selection & Dynamic Routing**: Optimize operational costs and latency by routing low-complexity or high-volume tasks to fast model tiers, reserving high-capability models (such as Sonnet) for tasks requiring deep reasoning.

---
### The most common transient HTTP error codes span across the 4xx (Client Error) and 5xx (Server Error) categories.

| Status Code | Name | Why It Is Transient  |
| --- | --- | --- |
| 408 | Request Timeout | The server took too long to receive the request. The network might just be slow right now.  |
| 429 | Too Many Requests | You have sent too many messages in a short amount of time. The server is rate-limiting you but will let you back in after a cooldown period.  |
| 409 | Conflict | The request conflicts with the current state of the server (e.g., trying to edit a file that someone else is saving at the exact same moment).  |
| 500 | Internal Server Error | A generic server stumble. This can be transient if the server briefly ran out of memory or a service restarted.  |
| 502 | Bad Gateway | A routing server or load balancer did not get a valid response from the main backend backend server because it is updating or restarting.  |
| 503 | Service Unavailable | The server is currently overloaded with traffic or down for quick maintenance.  |
| 504 | Gateway Timeout | A proxy server timed out waiting for the deep backend database or service to reply.  |

How to Handle Transient Errors 
When code runs into a transient error, it should not immediately give up. Instead, developers use specific patterns to handle them gracefully: 

* Retry Policies: Automatically send the request again. Popular tools like the .NET Polly Library watch for these exact codes to trigger a retry automatically.
* Exponential Backoff: Do not slam the server with immediate retries. Wait 1 second, then 2 seconds, then 4 seconds, giving the struggling server time to recover.
* Respect Headers: Servers often send a  header with a 429 or 503 code. This tells your application exactly how many seconds to wait before trying again.

```python
def classify_and_route_exception(error: Exception):
    """Categorizes API errors into retriable vs. terminal failure paths."""
    # Retriable: Rate limits (429) & server overloads (5xx)
    if getattr(error, "status_code", None) in [429, 500, 502, 503, 504]:
        return execute_exponential_backoff_retry(error)
    
    # Terminal: Invalid payloads (400), Auth (401/403), or Schema Mismatches
    else:
        return trigger_terminal_fallback_handler(error)

```

*Explanation*: This function applies the retriable vs. terminal test programmatically. Retriable status codes trigger exponential backoff queues to let server traffic clear, whereas terminal status codes fail fast to avoid wasting API budget on guaranteed failures.

### 2. Clear & Simple Explanation

Handling production failures requires distinguishing temporary bumps in the road from permanent brick walls.

* **Retriable Errors**: Think of a rate limit like hitting a red light. If you wait a few seconds and try again, the light turns green and your request goes through.
* **Terminal Errors**: Think of a malformed JSON payload like putting the wrong key in a lock. Turning the key ten more times won't unlock the door—you must fix the key before trying again.
* **Model Selection**: Match the model to the job. Don't use a heavy reasoning model for simple keyword extraction when a lightweight model can do it faster and cheaper.

### 5. Key Terms Note Section

**Key Technical Terms**:

* **Retriable Failure**: An operational exception (e.g., HTTP 429 rate limits, HTTP 503 server overloads) where repeating the identical request after a delay can plausibly succeed.
* **Terminal Failure**: An unrecoverable execution failure (e.g., malformed JSON payload, authentication failure, schema mismatch) where re-issuing the identical request will repeatedly fail.
* **Exponential Backoff**: An algorithm that exponentially increases delay intervals between successive retries to give overloaded servers time to recover.
* **Fail-Fast**: A design principle that halts execution immediately upon encountering an unrecoverable error to prevent cascade failures and conserve API tokens.
* **Dynamic Model Routing**: Programmatically directing prompts to different model tiers based on task complexity, latency requirements, and financial budgets.
* **Fallback Handler**: A pre-defined backup execution path (e.g., returning cached static data or escalating to human review) triggered when a terminal error occurs.

--- **Answer Key & Explanations** ---

1. B - An unescaped control character produces a malformed request (`400 Bad Request`). Repeating the identical request will fail every time, making it a terminal failure that must fail fast to avoid wasting API tokens.
2. A - An HTTP 429 error indicates temporary rate limiting. Because waiting allows rate limits to clear, it is a retriable failure that should be handled using exponential backoff with jitter.
3. D - Dynamic Model Routing optimizes costs and performance by routing simple tasks to lightweight, low-cost models while saving high-capability models for complex tasks requiring deep reasoning.
4. B - Repeating an identical invalid payload will yield the exact same schema validation error. It is a terminal error for that exact request; the system must alter the input (e.g., re-prompt with feedback) or execute a fallback path rather than performing blind retries.
5. B - The primary test for failure classification is single-question evaluation: *Would waiting and trying the exact same request again plausibly work?* If yes, it is retriable; if no, it is terminal.
