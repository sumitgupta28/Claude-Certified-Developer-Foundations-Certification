In Anthropic’s Claude ecosystem—particularly within Claude Code and Claude Managed Agents—the Orchestrator (the lead session coordinator) and the Subagent (the delegated worker instance) serve completely separate roles. 
They are designed to prevent context bloat, control blast radiuses, and maintain distinct operational bounds. 

A direct comparison of their memory, context, and permissions highlights how these roles are structurally separated: 
Memory, Context, and Permission Comparison 

| Feature | Orchestrator (Lead Agent) | Subagent (Worker Instance)  |
| --- | --- | --- |
| Primary Role | Owns intent classification, task decomposition, and final result synthesis. | Executes a single, narrowly bounded task delegated by the orchestrator.  |
| Context Window | Persistent & Growing; accumulates the core conversation history and subagent summaries. | Isolated & Ephemeral; starts fresh on invocation and gets discarded upon completion.  |
| Long-Term Memory | Reads/writes global project rules () and broad workspace memory stores. | Siloed to its specific configuration or completely blank unless explicit persistent memory is configured.  |
| Tool Permissions | Broad / Root Access; can run full shells, orchestrate workflows, and spawn processes. | Restricted / Scoped; restricted to specific sub-tools (e.g., read-only, plan-only, or code-review limits).  |
| Data Visibility | Sees the entire session trajectory, tool histories, and all subagent final outputs. | Only sees the exact context, instructions, and files passed down by the orchestrator.  |

**Deep-Dive: Memory** 

1. Orchestrator Memory: The orchestrator maintains global project context. In tool ecosystems like Claude Code, it relies heavily on configuration files like  to guide project identity, testing commands, and style guides.
   For Claude Managed Agents, it links to multi-session, version-controlled Memory Stores that persist across completely separate user sessions. 
3. Subagent Memory: By default, subagents suffer from a "game of telephone"—they cannot natively see what other sibling subagents have learned.
   They do not share memory with peers. However, they can be configured with targeted persistent memory (e.g.,  in Claude Code), which isolates a personal  directory.
   This allows a specific worker to remember localized habits, like codebase conventions, without cluttering the orchestrator's thoughts. 

**Deep-Dive: Context Management**
The entire orchestrator-subagent architecture exists primarily to defeat context degradation. 

1. Context Isolation: If an agent reads 50 files to fix a single line of code, doing so in the main chat thread wastes tokens and degrades Claude's focus. Instead, the orchestrator invokes a subagent using the  tool. 
2• The Merge Phase: The subagent consumes thousands of tokens evaluating the files in its own separate sandbox. When it finishes, it returns a tight, dense summary back to the orchestrator.
The subagent's temporary context window is burned, keeping the orchestrator's context window lean, clean, and highly attentive. 

**Deep-Dive: Permissions & Blast Radius**

1. Least Privilege Execution: The orchestrator acts as a security gateway. Instead of giving a general agent blanket read/write/execute capabilities across a whole system, custom subagents are configured with strict, specialized permissions. 
2. Subagent Profiles: Built-in and custom configurations allow subagents to be locked down by risk profile. For example: 

 - Set to strictly read-only for parsing logs and codebases securely.
 - A read-only instance designed to think in parallel with active execution.
 - Granted read/write abilities to edit files or run specific testing blocks.

• Indirect Inheritance: Subagents inherit system safety indirectly. 
If the orchestrator's memory states "never touch server X," the orchestrator is responsible for gating that task and must not delegate dangerous tool actions down to its workers.
