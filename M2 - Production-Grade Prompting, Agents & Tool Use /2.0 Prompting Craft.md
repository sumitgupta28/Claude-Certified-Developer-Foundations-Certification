## [Production-Grade Prompting, Agents & Tool Use](https://anthropic-partners.skilljar.com/path/claude-certified-developer-foundations/production-grade-prompting-agents-tool-use/486743/scorm/3k33sihfb1tww)

### 1. Problem Statement

Prompts that perform well during interactive, manual testing frequently break in production when exposed to untested, variable inputs. Developers often default to appending more text or rephrasing instructions, which increases prompt verbosity without fixing the underlying structural deficiencies that cause format drift, scope creeping, or parsing errors.

---

### 2. Summary

* **Diagnostic Iteration Loop:** Production engineering requires diagnosing *why* a prompt fails (missing output constraint, underspecified system prompt, missing examples, or unhandled variant) before adding text.
* **Four Structural Techniques:**
    1. **System Prompts:** Establish persistent behavioral contracts, roles, and boundaries across multi-turn interactions to prevent scope and tone drift.
    2. **XML Tags:** Provide unambiguous structural boundaries separating instructions, context, and example data to prevent boundary crossing.
    3. **Few-Shot Examples:** Show concrete input-output demonstration pairs when descriptions alone fail to pin down exact casing or syntax.
    4. **Output Constraints:** Explicitly define expected response shapes, field names, and stopping boundaries independent of content.


* **API-Level Structured Outputs:** Shifts reliability enforcement from prompt instructions to token-level constrained decoding via the Claude API using JSON Schema (`output_config.format`) or Strict Tool Use (`strict: true`).
* **Architectural Trade-offs:** Schema compilation adds initial latency (cached for 24 hours), injected system tokens increase context overhead, prefilling assistant messages is incompatible with JSON outputs, and code must still evaluate `stop_reason` (`refusal` or `max_tokens`).

---

### 3. Clear & Simple Explanation

When building production systems with Claude, relying on "please return JSON" in a prompt is risky because language models can occasionally return prose or wrong casing.

To fix output issues, start by diagnosing the exact failure:

  * **Wrong shape/JSON?** Add an **Output Constraint**.
  * **Model drifting or acting out of role?** Strengthen the **System Prompt**.
  * **Structure invented/hallucinated?** Provide **Few-Shot Examples**.
  * **Data and instructions mixing up?** Wrap inputs in **XML Tags**.

For absolute reliability in code pipelines, bypass prompt instructions entirely and use **Structured Outputs** at the API layer. This forces Claude’s output generator to only pick valid tokens matching your exact JSON Schema. While this guarantees structural correctness, remember that initial schema compilation adds a brief setup latency, and you must still handle cases where generation cuts off early due to token limits.

### 4. Real-World Application

**Scenario:** An enterprise automated ticket ingestion and routing engine receiving raw customer support emails, classifying the issue type, extracting key parameters, and invoking routing microservices.

**Architecture Workflow:**

```
[ Incoming Customer Email ]
            │
            ▼
┌────────────────────────────────────────────────────────┐
│  Spring Boot / Python Router Service                   │
│  - Encloses raw input in <ticket> XML tags             │
│  - Sets System Prompt (Role + Scope)                   │
│  - Attaches strict JSON Schema (output_config.format)  │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│  Anthropic API (Constrained Decoding Engine)           │
│  - Evaluates Schema Grammar Cache                      │
│  - Generates exact JSON payload matching schema        │
└──────────────────────────┬─────────────────────────────┘
                           │
            ┌──────────────┴──────────────┐
            ▼                             ▼
┌────────────────────────┐    ┌────────────────────────┐
│ stop_reason: "end_turn"│    │ stop_reason: "max_tok" │
└───────────┬────────────┘    └───────────┬────────────┘
            │                             │
            ▼                             ▼
┌────────────────────────┐    ┌────────────────────────┐
│ Parse JSON Payload &   │    │ Route to Fallback /    │
│ Route to Queue         │    │ Retry Handler          │
└────────────────────────┘    └────────────────────────┘

```

**Implementation Details:**

1. **XML Isolation:** Raw email content is wrapped in `<ticket>` tags so user inputs cannot inject prompt instructions.
2. **System Prompt Contract:** Sets the permanent agent scope ("You are an enterprise triage engine...").
3. **API Constrained Decoding:** Uses `output_config.format` with a JSON schema defining fields `category`, `urgency_score`, and `account_id`.
4. **Resilience Check:** Downstream code inspects `stop_reason`. If `"end_turn"`, it directly deserializes JSON without requiring additional sanitization. If `"max_tokens"` or `"refusal"`, it routes to a human fallback queue.

### 5. Key Technical Terms

* **Output Constraint:** Directives in a prompt specifying the exact structure, casing, or field boundaries expected in a response.
* **System Prompt:** A persistent instruction layer in the API set outside user turns to enforce roles, constraints, and behavioral contracts.
* **XML Tags:** Structural markers (e.g., `<input>`) used to separate context, instructions, and data boundaries clearly for the model.
* **Few-Shot Examples:** Demonstration pairs of input and ideal output embedded in the prompt to illustrate complex or exact patterns.
* **Structured Outputs:** An API feature that enforces schema compliance at generation time rather than relying solely on prompt instructions.
* **Constrained Decoding:** Token-by-token generation restriction enforced by the API, allowing only tokens that keep the output compliant with a JSON Schema.
* **Strict Tool Use:** A parameter (`strict: true`) on tool definitions ensuring argument payloads generated by Claude conform strictly to the specified input schema.
* **Schema Compilation Latency:** The initial processing delay incurred when the API converts a new JSON schema into a constrained grammar representation.
* **Stop Reason:** An API response metadata field indicating why model generation ended (e.g., `end_turn`, `max_tokens`, `refusal`).
* **Assistant Message Prefilling:** A prompt technique of providing the beginning of the assistant's response in the API payload, which is incompatible with structured output JSON schemas.

5. When incorporating few-shot examples into a classification prompt, Claude occasionally confuses example input content with the actual active instruction payload. Which structural technique eliminates this ambiguity?

* A) Encapsulating individual input-output example pairs within distinct XML tags (e.g., `<sample_input>` and `<ideal_output>`).
* B) Passing few-shot examples as system-level tool definitions using the tool use API.
* C) Increasing the max token limit so Claude reads further down the prompt context.
* D) Converting all few-shot examples into plain-text descriptive instructions without concrete data.

---

--- **Answer Key & Explanations** ---

1. **B** - Initial requests with a new JSON schema incur schema compilation latency while the API builds a constrained grammar (which is cached for 24 hours). Parsing failures in downstream services despite schema enforcement occur when code assumes valid JSON without checking if execution stopped prematurely due to `stop_reason: max_tokens` or was blocked via `stop_reason: refusal`.
2. **A** - System prompts define the persistent behavioral contract, scope, and rules that persist across multi-turn interactions. When scope drift occurs deeper in a conversation, it indicates an underspecified system prompt.
3. **C** - In the Claude API, JSON outputs enforced via `output_config.format` and assistant message prefilling are mutually exclusive because constrained decoding controls the complete root payload generation from the beginning token.
4. **D** - While `strict: true` guarantees that tokens generated under full execution strictly conform to the JSON schema, edge cases such as token limit truncation (`stop_reason: max_tokens`) or safety refusals (`stop_reason: refusal`) cut off generation before a valid schema object is completed.
5. **A** - Using XML tags creates distinct boundary layers between instruction text, system prompts, and example data. This prevents the model from reading content within few-shot examples as active instructions for the current user input.
