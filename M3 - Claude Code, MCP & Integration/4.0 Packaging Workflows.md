### Packaging a workflow as a plugin: skills, custom commands, and marketplace install

### 1. Problem statement

Manual distribution and setup of local developer configurations (such as `.claude` memory files, rules, hooks, and subagents) leads to configuration drift, high operational overhead, and runtime errors across development teams. Software organizations require a standardized, version-controlled, and centrally governable packaging and distribution mechanism to share AI workflows, custom commands, security guardrails, and tool integrations across diverse execution environments (Claude Code, Messages API, Agent SDK, and Claude Managed Agents) without introducing environment-specific failures or dropping critical security guardrails.

---

### 2. Summary

* **Skills as Universal Workflows**: A skill is a portable Markdown file (`SKILL.md`) located in `.claude/skills` with YAML frontmatter specifying matching criteria and execution steps. Skills run on [Claude Code](https://anthropic-partners.skilljar.com/path/claude-certified-developer-foundations/claude-code-mcp-integration/486744/scorm/173ln01ww7hgd), Messages API, Agent SDK, and Claude Managed Agents.
* **Runtime Execution Differences**:
  * *Claude Code*: Discovered from `.claude/skills` on the filesystem; loads on description match or explicit invocation and runs in interactive terminal sessions under active permission modes and deny rules.
  * *Messages API*: Executes inside API container environments without access to host-bound CLI tools.
  * *Agent SDK*: Managed via `settingSources` runtime configurations.
  * *Claude Managed Agents*: Executes in managed cloud agent environments.


* **Three Critical Portability Rules**:
  1. *Description as Matching Criterion*: The model selects skills on demand by matching user requests against the skill's description; vague descriptions cause invocation failures across all runtimes.
  2. *Environment Decoupling*: Avoid embedding local filesystem assumptions or OS-specific shell commands in skill bodies, as containerized runtimes (e.g., Messages API) lack local command-line tools.
  3. *Explicit Subagent Attachment*: Subagents execute in clean context states and never inherit parent session skills automatically; skills must be explicitly declared for subagents across all runtimes.


* **Custom Commands & Entry Points**:
  * Skills are the recommended format for both explicit (`/skill-name`) and automatic model invocation.
  * Set `disable-model-invocation: true` in YAML frontmatter for workflows requiring strict, explicit-only user triggering.
  * Legacy `.claude/commands/` directory format is deprecated.
  * Plugin commands are automatically namespaced (`/plugin-name:command-name`) to eliminate naming collisions across plugins.


* **Plugin Architecture & Marketplace Distribution**:
  * Plugins bundle skills, hooks, subagents, settings, and Model Context Protocol (MCP) servers into a single versioned unit.
  * Distributed via marketplaces (catalogs of plugins). Official Anthropic marketplace is active by default; third-party GitHub catalogs are added via `/plugin marketplace add <owner/repo>`.


* **Enterprise Governance & Precedence Hierarchy**:
  * Enterprise administrators deploy plugins globally using managed settings.
  * Configuration Scope Hierarchy: Managed Settings > User Settings > Project Settings. Managed settings sit at the top and cannot be overridden by user or project files.
  * Administrators restrict plugin sources using a managed marketplace allowlist and automatically push catalogs to team workstations without manual developer intervention via `extraKnownMarketplaces`.


* **Cost, Complexity, and Risk Tradeoffs**:
  * *Cost*: Skills incur context overhead upon activation; plugins incur initial packaging and maintenance overhead.
  * *Complexity*: Hardcoding absolute local paths inside skills breaks portability across different teammate machines.
  * *Risk*: Local security guardrails (deny rules/hooks) do not transfer to teammates unless explicitly included inside the distributed plugin bundle.

### 3. Clear & Simple Explanation

When configuring Claude Code, developers often create helpful rules, automated security checks (hooks), and specialized instructions in their local `.claude` folder. Sharing these setups manually with teammates is tedious and error-prone.

* **Skills**: Reusable step-by-step instructions written in Markdown. Claude reads the description at the top of the file to determine when to run the skill automatically, or you can call it directly using a slash command (`/skill-name`).
* **Runtime Portability**: Because skills can run in interactive terminals, cloud APIs, or background SDK workers, skill steps should never assume local software or specific file paths exist on the host system.
* **Subagents**: Subagents always start in a fresh, clean context. They do **not** automatically inherit any skills loaded by the main parent session, so you must explicitly pass required skills to subagents.
* **Plugins**: An installer package that bundles skills, security hooks, subagent definitions, and tool connectors (MCP servers) together. Instead of asking teammates to copy multiple files, they install one versioned plugin.
* **Namespacing**: To keep commands organized and prevent two plugins from overriding each other (e.g., if both have a `test` command), plugin commands are automatically prefixed with the plugin name (`/plugin-name:command-name`).
* **Enterprise Control**: Organization admins use managed settings at the top level of the configuration hierarchy to control which plugin marketplaces developers can access and automatically register approved internal plugin stores across all developer machines.

### 4. Real-World Application

**Scenario**: A financial technology company needs to standardize a secure microservice deployment workflow across 200 software engineers. The workflow requires executing static analysis, running unit tests, executing database migration scripts, connecting to a centralized compliance MCP server, and delegating code security audits to an isolated subagent.

**Architecture Scenario & Execution Flow**:

1. **Packaging**: The engineering enablement team packages skills, pre-commit hooks, subagent definitions, and MCP server endpoints into a single, versioned plugin named `fintech-deploy`.
2. **Enterprise Governance**: Security administrators configure managed settings at the enterprise level, enforcing a managed marketplace allowlist restricted to `[github.com/fintech-corp/plugins](https://github.com/fintech-corp/plugins)` and deploying `extraKnownMarketplaces` to automatically register the catalog on all developer machines.
3. **Execution**: A developer runs `/fintech-deploy:release` in Claude Code. The namespaced command loads the `release` skill, enforces pre-commit hooks, interfaces with the compliance MCP server, and explicitly attaches security skills to a newly spawned, isolated subagent.

### 5. Key Terms Note Section

**Key Technical Terms**:

* **Skill**: A portable Markdown file (`SKILL.md`) located in `.claude/skills` containing YAML frontmatter metadata and execution steps loaded on demand by Claude.
* **Custom Command**: A user-triggered slash-command shortcut used to invoke specific procedures directly in Claude Code (`/skill-name`).
* **Plugin**: A versioned, installable bundle combining skills, hooks, subagents, settings, and MCP servers into a single shareable unit.
* **Plugin Marketplace**: A catalog repository (official Anthropic catalog or custom GitHub repository) used to host, discover, and distribute Claude Code plugins.
* **Namespacing**: The automatic prefixing of plugin commands with the plugin name (e.g., `/plugin-name:command`) to prevent command collisions across different plugins.
* **Managed Settings**: Organization-level settings deployed by administrators that sit at the top of the configuration hierarchy, overriding user and project settings.
* **extraKnownMarketplaces**: A managed setting parameter used to automatically distribute and register approved plugin marketplaces across all developer environments.
* **Model Context Protocol (MCP) Server**: An external interface integrated into Claude Code or plugins to provide standardized data access and tool execution capabilities.
* **Subagent**: An isolated execution process spawned by Claude Code that starts with a clean context and does not automatically inherit skills from the parent session.

--- **Exam Practice** ---

1. A lead developer designs a custom skill in `.claude/skills/deploy.md` for a deployment workflow. The skill executes successfully during local testing in Claude Code interactive terminal sessions. However, when the same skill is deployed to an automated build pipeline running via the Messages API, the workflow fails with command execution errors. What is the root cause of this failure based on skill portability rules?

* A) The Messages API runtime requires skills to be located in `.claude/commands/` rather than `.claude/skills/`.
* B) The skill body contains steps that shell out to local binaries or environment-specific CLI tools not present inside the API container execution environment.
* C) The Messages API automatically disables all custom skills unless `disable-model-invocation: true` is explicitly configured.
* D) Custom skills executed via the Messages API must be deployed at the enterprise managed settings scope to obtain container execution privileges.

2. An enterprise administrator needs to distribute a set of proprietary Claude Code plugins across 500 engineering workstations. The administrator must enforce two constraints: (1) developers must only be allowed to add plugins from an approved internal GitHub repository, and (2) the approved internal marketplace must be automatically registered on all developer machines without requiring developers to manually execute `/plugin marketplace add`. Which combination of settings achieves this objective?

* A) Set `plugin-allowlist` in project-level `CLAUDE.md` files and distribute a shell script to run `/plugin marketplace add` upon terminal launch.

* C) Define project-level settings with `disable-model-invocation: true` and specify the repository URL in `.claude/skills/marketplace.md`.
* D) Configure managed settings at the administrative scope with a managed marketplace allowlist and populate `extraKnownMarketplaces`.

3. A developer configures a complex code refactoring task in Claude Code. The parent session loads a specialized skill (`/refactor-architecture`) to guide the refactoring strategy. During execution, the parent session spawns an isolated subagent to process a specific sub-module. The subagent fails to apply the rules specified in `/refactor-architecture`. What fundamental subagent execution principle explains this behavior?

4. An automated database migration procedure should only be executed when a developer explicitly types `/db-migrate` in Claude Code. The workflow must NEVER be triggered automatically by Claude based on task description matching. How should the skill's frontmatter be configured to guarantee this explicit-only invocation behavior?

* A) Set `auto-invoke: false` in the YAML frontmatter of `.claude/skills/db-migrate.md`.
* B) Set `scope: explicit-command` in `.claude/commands/db-migrate.json`.
* C) Set `disable-model-invocation: true` in the YAML frontmatter of `.claude/skills/db-migrate.md`.

5. A platform engineer packages a local developer setup into a plugin and distributes it to team members via an internal marketplace. The original developer setup relied on a local deny rule hook to block unauthorized file deletion. Teammates install the plugin successfully, but report that unauthorized file deletion operations are not being blocked on their machines. What is the root cause of this security discrepancy?

* A) Deny rules and hooks cannot be executed inside plugins due to marketplace security sandbox restrictions.
* B) Local security guardrails and deny rules present on the author's machine are not inherited by teammates unless explicitly included in the plugin bundle.
* C) Plugins automatically override local deny rules with default permissive policies upon installation.
* D) Project-level settings take precedence over plugin guardrails, causing project configuration to override the deny rule.

---

--- **Answer Key & Explanations** ---

1. B - A primary portability rule for skills is to avoid assuming local tools or filesystems exist. While Claude Code runs in an interactive terminal session with host shell access, the Messages API executes inside a container environment without local binaries, causing host-dependent shell commands to fail.
2. D - Managed settings reside at the top of the configuration hierarchy (overriding user and project settings). Administering a managed marketplace allowlist restricts permitted plugin sources, while configuring `extraKnownMarketplaces` automatically registers the marketplace across all user environments without requiring manual user commands.
3. A - Subagents run in isolated execution states starting with a clean context. Subagents do not automatically inherit skills loaded by or available to the parent session; skills must be explicitly assigned to subagents across all runtimes.
4. C - Setting `disable-model-invocation: true` in the skill's YAML frontmatter prevents Claude from automatically matching and triggering the skill based on prompt descriptions, restricting invocation exclusively to explicit user slash commands (`/skill-name`).
5. B - Plugins only package components explicitly declared in the plugin bundle. Local guardrails, deny rules, or hooks residing on the author's machine are not automatically transferred or enforced on teammates' machines unless specifically included inside the plugin package.
