### Claude Code agent loop, permission modes, settings, and where a human gate goes

### 1. Problem statement

Deploying agentic development tools in terminal environments introduces a fundamental tension between software engineering velocity and system safety. Unrestricted agent loops can inadvertently execute destructive shell commands, overwrite sensitive environment variables, or alter critical codebase logic. Conversely, requiring human approval for every trivial file read or formatting tweak creates latency and developer fatigue. Engineering teams need a structured, hierarchical governance framework to control agent autonomy based on risk and execution scope.

### 2. Summary

The [Claude Code, MCP & Integration](https://anthropic-partners.skilljar.com/path/claude-certified-developer-foundations/claude-code-mcp-integration/486744/scorm/173ln01ww7hgd) module details how Claude Code manages agent execution, permission states, configuration resolution, and human review gates:

* **Lifecycle Task Execution**: Claude Code executes tasks sequentially through three phases:
  1. **Explore**: Reads codebase files and traces execution logic to build an accurate mental model.
  2. **Plan**: Generates a structured proposal describing intended file edits and execution steps.
  3. **Code**: Writes and executes approved changes.


* **Permission Modes**:
  * `default`: **Auto-approves file reads**; requires explicit user approval for file edits and shell commands. Baseline for unfamiliar codebases.
  * `acceptEdits`: **Auto-approves file edits within the working directory** to accelerate trusted refactoring.
  * `plan`: Keeps the agent strictly within the exploration phase, blocking all file modifications and shell execution.
  * `auto` / `dontAsk`: Automates routine operations with reduced prompt frequency.
  * `bypassPermissions`: Bypasses all prompt checks and safety guards; carries severe risk on non-isolated hosts.


* **Settings Resolution Hierarchy**:
  * **Enterprise level** (`managed-settings.json`): Administrator-defined controls that cannot be overridden by users or projects.
  * **User level** (`~/.claude/settings.json`): Global developer preferences applied across all machine repositories.
  * **Project level** (`.claude/settings.json`): Shared team rules and tool permissions committed directly to git.
  * **Local project level** (`.claude/settings.local.json`): Developer-specific, git-ignored local overrides.


* **Governance Rule**: Deny rules deterministically override allow rules at every configuration layer. Managed enterprise deny rules persist even if a developer enables a bypass flag.
* **Worst-Case Cost Gate Placement**:
  * *Low-Cost / Reversible*: Auto-approve routine formatting and localized file edits (`acceptEdits`).
  * *High-Cost / Irreversible*: Require manual prompts or enforce deny rules for edits outside the workspace, destructive terminal operations, or security files.
  * *Sensitive Code*: Require mandatory human code review prior to merging pull requests regardless of agent self-evaluation scores.



### 3. Clear & Simple Explanation

Claude Code works like an automated paired developer operating in your command terminal:

* **Look Before Jumping**: It spends time reading project files and outlining a plan before writing any code.
* **Dialing In Freedom**: You control its boundaries using modes. You can force it to only read and plan (`plan`), ask before touching anything (`default`), quickly edit working files (`acceptEdits`), or turn off safety checks entirely (`bypassPermissions`).
* **Stacked System Rules**: IT managers set non-negotiable enterprise rules at the top. Project teams set repository rules in the middle, and developers set personal preferences at the bottom. A "Deny" rule always beats an "Allow" rule.
* **Smart Oversight**: Require human approval whenever an action could break production or delete unrecoverable data. Automate minor, easily fixable tasks like code cleanup.

### 5. Key Terms Note Section

Maintaining strict security posture across agentic CLI workflows requires precise knowledge of permissions and configuration tiers.

**Key Technical Terms**:

* **Agent Loop**: The core iterative execution cycle where Claude processes context, invokes tools, receives outputs, and continues until a task is finalized.
* **Exploration Phase**: The initial phase where Claude Code inspects repository files and traces code paths before making edit proposals.
* **Plan Mode**: A permission mode that holds the agent strictly in the exploration phase, preventing all file writes and terminal commands.
* **acceptEdits Mode**: A permission setting that automatically approves file edits within the local workspace while gating external writes and shell execution.
* **managed-settings.json**: The top-level enterprise configuration file deployed by system administrators enforcing non-overridable safety rules.
* **Deny Rule**: A configuration policy that explicitly blocks designated files or tool calls, taking precedence over all allow rules across all configuration tiers.
* **Worst-Case Cost**: The evaluation metric used to determine whether an agent action requires an interactive human approval gate based on reversibility and risk.

* A) The local allow rule takes priority over enterprise defaults.
* B) The `bypassPermissions` flag disables all managed settings and executes the edit.

4. What functional milestone marks the transition from the **Explore** phase to the **Plan** phase in the Claude Code execution loop?

* A) Automated execution of unit tests in isolated runtime environments.
* B) Direct write operations being applied to codebase files.
* C) Ingestion of user-level settings overrides from `~/.claude/settings.json`.

5. How does Claude Code resolve a conflict where a project file `.claude/settings.json` contains an allow rule for `npm test`, but `~/.claude/settings.json` contains a deny rule for `npm` execution?

* A) The deny rule blocks execution because deny rules strictly override allow rules across all configuration levels.
* B) The allow rule executes because project settings override user settings.
* C) Both rules are ignored, forcing an automatic fallback to `bypassPermissions`.
* D) The command executes automatically, but logs a warning to the console.

---

--- **Answer Key & Explanations** ---

1. **B** - `plan` mode holds Claude Code in the exploration phase, blocking file edits and shell commands. Placing this setting in `~/.claude/settings.json` applies it at the user level across every project on the machine.
2. **C** - Enterprise managed settings (`managed-settings.json`) cannot be overridden by user or project files, and deny rules deterministically take precedence over allow rules and bypass flags across all tiers.
3. **A** - Low-stakes, easily reversible edits confined to the local working directory (such as formatting fixes) carry negligible worst-case cost, making them suitable for auto-approval (`acceptEdits`).
4. **D** - The Plan phase creates a structured description of proposed modifications after the agent finishes reading files and tracing repository logic during the Explore phase.
5. **A** - A deny rule always wins over an allow rule regardless of setting hierarchy or configuration level. The deny rule for `npm` at the user level strictly blocks execution.
