### Choosing where a Claude workload runs and versioning what ships

### 1. Problem statement

Deploying Claude workloads without aligning platform choices to existing customer cloud infrastructure, identity systems, and compliance boundaries leads to lengthy security re-evaluations and data residency violations. Furthermore, using dynamic convenience aliases (e.g., unpinned model IDs) in production causes silent, untracked breaking changes when upstream models update, risking unexpected output regressions without automated rollback capabilities.

### 2. Summary

Selecting a deployment target and managing model releases requires matching customer infrastructure trust with strict version locking:

* **Platform Selection Driven by Customer Cloud**: Platform selection is guided by where the customer already maintains identity, billing, and compliance agreements:
  * **First-party Claude API**: Anthropic-hosted environment; receives new features first. Ideal when no cloud binding or strict regional residency constraints exist.
  * **Claude Platform on AWS**: Accessed through the customer's AWS account using Anthropic model IDs and lifecycle, but inference is Anthropic-operated outside the customer AWS boundary.
  * **Claude in Amazon Bedrock**: Uses the Messages API (`/anthropic/v1/messages`) with broad feature parity; data remains within the customer's AWS boundary. (Legacy integration uses `InvokeModel`/`Converse` APIs with ARN-versioned identifiers).
  * **Google Vertex AI**: Uses Google Cloud IAM, billing, and regional/global endpoints for data residency compliance.
  * **Microsoft Foundry**: Provides two hosting forms—*Hosted on Azure* (inference running end-to-end on Azure infrastructure) and *Hosted on Anthropic* (inference on Anthropic infrastructure).


* **Version Pinning & Snapshot Locking**: Convenience aliases (e.g., `claude-haiku-4-5`) evolve over time and resolve differently across platforms. Production deployments must pin explicit model snapshot IDs (e.g., `claude-haiku-4-5-20251001` or platform-specific snapshot formats) so upstream model updates remain deliberate, controllable decisions.
* **Eval-Gated Promotion**: Releases should route traffic to candidate model versions, evaluate performance against a pinned baseline score using an evaluation suite, and execute automated promotion or rollback based on results.
* **Trade-Offs**: Pinning versions and maintaining rollback paths add release process overhead. Moving aliases are acceptable only for throwaway prototypes that never reach production.

### 2. Clear & Simple Explanation

Deploying and versioning an AI model is similar to managing a commercial shipping agreement:

1. **Choosing the Delivery Carrier (Platform Selection)**: If your company already holds an enterprise contract and security badge with AWS, Google Cloud, or Azure, you ship through that carrier. This reuses your existing security clearance, identity badges, and local legal agreements (data residency) rather than building a new shipping process from scratch.
2. **Pinning the Model Version (Fixed ID vs. Dynamic Alias)**: Using an unpinned alias like `claude-haiku-4-5` is like addressing a package to "The Current Manager." If the manager changes overnight, your package goes to a new person without notice. Pinning a full snapshot ID (like `claude-haiku-4-5-20251001`) guarantees that your package is delivered to the exact same individual every single time.
3. **Eval-Gated Promotion (Taste Test Before Launch)**: Before switching to a new recipe across all restaurants, you serve sample plates to 10% of customers and test the dishes against a master taste rubric. If the quality drops, you instantly revert to the previous recipe.

### 4. Real-World Application

**Scenario: Regulated Healthcare Patient Assistant Deployment**

A healthcare enterprise deploys a Claude-powered patient assistant within an existing AWS environment subject to HIPAA and US data residency rules:

* **Platform Choice**: The organization deploys via *Claude in Amazon Bedrock* using the Messages API (`/anthropic/v1/messages`) to keep all patient payload processing inside the customer's AWS security perimeter and identity boundary.
* **Pinning Configuration**: The application microservice configuration explicitly pins the model snapshot ID (`anthropic.claude-3-5-sonnet-20241022-v2:0`) instead of an unpinned alias.
* **Canary Promotion Pipeline**: When testing a candidate model upgrade, CI/CD routes 10% of live traffic to the new snapshot while executing an automated **Eval Suite**. Responses are scored against a pinned baseline. If performance metrics pass, traffic scales to 100%; if an evaluation drop occurs, traffic automatically falls back to the retained prior snapshot.

### 5. Key Terms Note Section

Maintaining precision around cloud hosting perimeters and release engineering controls is necessary for architectural compliance and certification readiness.

**Key Technical Terms**

* **Deployment Platform**: The hosting infrastructure (First-party API, AWS Bedrock, Google Vertex AI, Microsoft Foundry) where Claude model inference, identity management, and compliance boundaries execute.
* **Moving Alias**: A dynamic model name pointer (e.g., `claude-haiku-4-5`) that updates automatically when new model iterations release, risking untracked production changes.
* **Pinned Model Snapshot**: An immutable, fully qualified model identifier (incorporating specific date suffixes or ARN version tags) that guarantees execution against fixed model weights.
* **Data Residency**: The legal and architectural requirement that ensures customer data and inference processing remain within defined geographical or cloud security perimeters.
* **Messages API**: The standardized API specification (`/anthropic/v1/messages`) used across first-party and cloud provider integrations to maintain feature parity across platforms.
* **Eval Deployment Gate**: An automated CI/CD pipeline gate where candidate model versions must meet or exceed a pinned baseline evaluation score before production promotion.
